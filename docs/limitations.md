# Limitations

What Med-Sum does not do yet, and what its checks let through.

- **Access control is built for one hospital on one machine.** Accounts, sessions, roles, staff management, patient records shared within an organisation, the audit log and the hardening above work. What it leaves out: medical registration numbers are not verified; there is no email, so setup and reset links are handed over by an admin; there is no second factor; every clinician of an organisation sees every patient of it (no per-patient or per-department restrictions, and no break-glass access); the first admin of an organisation is created from the command line; uploads and the database are not encrypted at rest; TLS is the deployer's job; the login limit is per API process; and a failed login with an unknown email is recorded without an organisation, so no admin sees it on the Audit log page.
- **The dev server has no script policy.** `npm run dev` injects inline scripts for hot reload, so it can't carry a `script-src`; it sets only `frame-ancestors 'none'`. The built app served by `vite preview` carries the strict policy in `frontend/vite.config.js` (scripts, images, frames and requests from its own origin; inline styles only, which the document pages need), and that policy is the baseline for any deployment.
- **Vision misreads are only caught where a PDF has a text layer.** A scan or photo has no independent text to compare the model's reading with, so a value read wrongly but consistently passes the checks. With a text layer, each value is looked for in its own row (next to its test or medicine name), with the row's own reference range taken out, so a misread that matches a number in another row, or a bound of its own range, is still caught; one that matches a number in its test name or unit passes. The fault check caught 110 of 130 such misreads, and all 20 it missed were on pages without a text layer.
- **A page too long for one call is joined only when its halves agree exactly.** A capped page is read again as a top and a bottom half that overlap, and joined only on a run of identical lines found in one place. A page in two columns can't be joined that way (each half reads part of one column, then part of the other), and neither can long paragraphs, which the model writes as single long lines that rarely come out the same twice. Such a page keeps no lines and goes to review.
- **A page that prints the end-of-page marker is caught only through its text layer.** A transcription stops at its end marker, and Ollama drops the marker from the reply, so on a scan or photo that prints it the rest of the page is lost with no sign. On a PDF with a text layer, or when a reply goes on after the marker, the document goes to review (LC-21).
- **Some wrong values pass the checks.** Every row of a results table must become a result, so a row the parse leaves out goes back to the parse, then to review. A result printed as a line of text rather than a table row has no such check: leaving it out is only an information note, so the document can still end verified (the 6 dropped results the fault check missed are all of this kind). A value equal to one of its own range bounds is sent to review when its row prints that number only inside the range (153 of 153 range bounds taken for the value were caught); one printed in its own cell as well is taken as the real value.
- **No medical codes or brand-to-generic mapping.** Medicines are kept as written (brands stay brands), and no LOINC, SNOMED or RxNorm codes are assigned: the local models aren't reliable enough to map them.
- **Lab reports and prescriptions only.** Any other document is kept, transcribed and marked for review, but not parsed.
- **Neither local model is yet safe enough for documents to be auto-verified.** In the first live evals, both models are above the 1% unsafe-error gate (`qwen3.5:4b` 10 of 204 clinical items, `gemma4:e2b` 27), and `qwen3.5:4b`'s `verified` documents still hold unsafe errors in 8 of 149 items. Until a run passes the gate, [ADR 0013](adr/0013-model-choice-after-the-first-live-evals.md) proposes sending every document to a clinician. See [Live eval results](eval-results.md). The MCP client eval hasn't been run. Signal precision and the escape rate need clinicians' reviews, so they have no numbers yet either.
- **The overview check doesn't test what an overview leaves out.** The overview judge found a shown overview that didn't name a recorded drug allergy. The check tests that what is said follows from the facts, not that what a clinician needs is said ([Overview judge](eval-judge.md)).
- **Clinicians' licences are not verified.** A medical registration number can be recorded on an account, but nothing checks it against a medical council's register.
- **Not validated clinically.** Nothing here has been tried by clinicians or on real documents. The synthetic dataset is varied in layout, but it was built by the same hands as the checks.
- **The overview check is strict and literal.** It compares words, not meanings. A number counts as in context when one of the words around it (three either side; six for a word such as "high" or "rising") is a word of what it belongs to, so two tests that share a unit in one list can still trade values, and an ordinary word missing from its fixed list leaves the overview out. Its layout is a first draft.
- **No container setup** yet. CI runs on GitHub (Go, Python with the fault check, and the frontend), but its eval-replay job skips its steps until replies have been recorded.
